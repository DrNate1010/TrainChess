# Contributing to TrainChess.org

Thank you for your interest in contributing to TrainChess.org!

TrainChess.org is an open-source chess analytics platform designed to help players understand their playing habits, identify recurring weaknesses, and improve through personalized, data-driven training recommendations.

We welcome contributions from developers, chess players, designers, testers, and anyone interested in helping the project grow.

## 1. Ways to Contribute

There are many ways to contribute to TrainChess.org, including:

- **Code:** Implement features, fix bugs, and improve performance.
- **Chess Analytics:** Develop and improve methods for identifying patterns, weaknesses, and opportunities for improvement across multiple games.
- **User Interface and Design:** Improve usability, accessibility, and the overall user experience.
- **Testing:** Identify bugs, write automated tests, and verify proposed changes.
- **Documentation:** Improve setup instructions, technical documentation, and user guides.
- **Feedback:** Suggest features, report problems, and share ideas for improving the platform.

Contributions of all experience levels are welcome.

## 2. Before You Start

Before beginning work on a contribution:

1. Check the existing GitHub Issues to see whether the problem or feature has already been discussed.
2. For significant changes, open an issue to discuss your proposal before starting implementation.
3. If an issue is already assigned to someone, coordinate with them before working on it.
4. Ask questions if anything is unclear.

Small fixes, such as correcting documentation or fixing an obvious typo, generally do not require prior discussion.

## 3. Reporting Bugs and Suggesting Features

When reporting a bug, please include:

- A clear description of the problem.
- Steps to reproduce it.
- Expected behavior and actual behavior.
- Relevant error messages, logs, or screenshots, when available.
- Your environment details when they may affect the issue.

When suggesting a feature, explain the problem it would solve, who would benefit from it, and how you think it could work.

Please search existing issues before creating a new one to avoid duplicates.

## 4. Development Workflow

We use Git and GitHub to manage development.

The general contribution process is:

1. Fork the repository.
2. Clone your fork and create a separate branch for your changes.
3. Make your changes and test them locally.
4. Commit your work with a clear, descriptive commit message.
5. Push your branch to your fork.
6. Open a pull request against the project's main repository.
7. Respond to review feedback and make any necessary revisions.

Avoid combining unrelated changes into a single pull request. Smaller, focused pull requests are generally easier to review and maintain.

## 5. Code Quality and Testing

Contributions should follow the project's existing conventions and architecture.

Please:

- Write clear, maintainable code.
- Use descriptive names for variables, functions, components, and other identifiers.
- Avoid unnecessary complexity and duplicated logic.
- Add or update tests when appropriate.
- Verify that existing functionality continues to work.
- Update documentation when a change affects setup, behavior, or public interfaces.
- Avoid introducing unnecessary dependencies.

Specific formatting rules, linting tools, and testing commands will be documented as the project establishes its development workflow.

## 6. Chess Analytics Standards

Because TrainChess.org provides chess analysis and personalized training recommendations, analytical contributions should prioritize accuracy, transparency, and usefulness.

When contributing to analytical features:

- Explain the reasoning behind new metrics or detection methods.
- Include representative positions or games when useful for validating a finding.
- Add tests for important calculations and edge cases.
- Distinguish engine evaluations from conclusions about a player's recurring habits.
- Avoid presenting uncertain patterns as definitive conclusions.
- Consider whether recommendations are understandable and actionable for the intended player.

Where possible, include example positions, test games, or reproducible datasets that demonstrate the behavior of a proposed change. Do not publish another person's private games or personal data without appropriate permission.

## 7. Pull Request Guidelines

Every pull request should include:

- A concise description of the changes.
- The reason for the change and the problem it addresses.
- Any related issue numbers.
- Testing performed and its results.
- Screenshots or examples for user-facing changes, when applicable.
- Any relevant documentation updates.

Pull requests will be reviewed for correctness, maintainability, compatibility, and consistency with the project's goals.

Maintainers may request changes, ask questions, or decline contributions that do not fit the project's direction or quality standards.

Please be patient during the review process.

## 8. Security and Privacy

Do not include passwords, API keys, access tokens, or other secrets in commits, issues, or pull requests.

Do not submit private user data, personal information, or chess games without appropriate permission.

If you discover a security vulnerability, report it through the project's designated private security reporting channel rather than publicly disclosing exploitable details.

## 9. Community Expectations

All contributors are expected to be respectful, constructive, and welcoming.

Give feedback about ideas and code rather than attacking individuals. Differences of opinion should be handled professionally, and contributors of all backgrounds and experience levels should be treated fairly.

Harassment, discrimination, and deliberately disruptive behavior are not acceptable.

Please refer to the project's Code of Conduct for further details.

## 10. License

By submitting a contribution, you agree that your contribution may be distributed under the open-source license used by TrainChess.org.

Please ensure that you have the right to submit the code, documentation, or other material you contribute. Do not submit material copied from sources whose licensing terms are incompatible with the project's license.

The project's chosen license is available in the repository's `LICENSE` file.

## 11. Thank You

Every useful contribution helps make TrainChess.org better.

Whether you are fixing a small bug, improving a chess analysis algorithm, writing documentation, or helping another contributor get started, we appreciate your time and effort.

Thank you for helping build TrainChess.org!
